### 历史版本：带沙盒签名的真实输入源验证

执行：

```bash
bash Scripts/verify-integration.sh --include-system-pinyin --activate-apps
```

测试程序与正式应用共用 `InputSourceService`、`LockController` 和 `LockEngine`，使用独立 bundle identifier、偏好域及相同的 App Sandbox entitlement。

| 锁定目标 | 第 1 次恢复 | 第 2 次恢复 | 第 3 次恢复 |
| --- | ---: | ---: | ---: |
| ABC | 41.9 ms | 17.4 ms | 16.9 ms |
| 微信输入法 | 16.9 ms | 13.6 ms | 12.9 ms |
| 系统简体拼音 | 14.9 ms | 16.1 ms | 14.5 ms |
| 系统繁体拼音 | 37.9 ms | 14.2 ms | 16.8 ms |

耗时从测试程序调用切换接口开始，到重新观察到锁定目标为止；观察间隔为 10 毫秒。12 次均低于初始的 500 毫秒验收目标。这是本机有限样本，不能视为所有应用、负载和输入法组合下的延迟保证。

同时通过：

- 四种目标解锁后，切换到其他输入源不会被恢复。
- 使用真实 `EnableSecureEventInput` / `DisableSecureEventInput`，验证自动暂停、暂停期间不争抢、结束后恢复原目标。
- 停止控制器后不再切回；重新创建控制器时从持久化配置恢复目标。
- 注入工作区的休眠、唤醒通知，验证控制器的暂停和恢复路径。
- Safari、文本编辑、终端成为前台应用后，仍能恢复目标。
- 连续制造真实输入源切换后，触发频繁争抢暂停；手动重试后恢复。

这次测试开始时，可用输入源为 ABC 和微信输入法。系统简体、繁体拼音的模式已启用，但其父输入法未启用，因此不在可选择列表内；测试临时启用父输入法，结束后还原。测试结束后的实时查询确认仍只有 ABC 和微信输入法可用，当前输入源已恢复为原来的微信输入法。

### 历史版本：省电调度验证

调整为按状态调度后，21 项单元测试、Release 构建和完整沙盒集成验证再次通过。

集成程序向真实 `LockController` 注入可记录调用次数的模拟输入源服务，并隔离真实的输入源和前台应用通知，以验证定时器本身的行为：

- 未锁定时，1.25 秒内输入源与安全输入查询均为 0。
- 稳定锁定时，1.3 秒内查询当前输入源 3 次，没有枚举输入源列表。
- 模拟输入源变化但不发送通知，兜底检查在 225.2 毫秒后完成恢复并正确计数。
- 模拟接口接受请求但实际未切换，在 3 次尝试后进入故障暂停；暂停后 600 毫秒内无查询，手动重试可恢复。
- 安全输入暂停期间，1.25 秒内只发生低频安全输入状态查询，没有查询当前输入源、枚举列表或执行切换；结束后正常恢复。
- 注入显示器休眠/唤醒、电脑休眠/唤醒、会话停用/激活通知，验证暂停期间无定时查询、返回后能恢复；解锁后也停止定时查询。

随后用真实系统输入源执行完整验证，ABC、微信输入法、简体拼音、繁体拼音的 12 次恢复耗时为 **13.6–22.8 毫秒**。Safari、文本编辑、终端切换、真实安全输入暂停/恢复、有限重试和累计统计均通过。

新版启动后，对开启锁定的 Release 进程运行 `top -l 6 -s 2` 采样约 10 秒：间隔样本的 CPU 均显示 **0.0%**，内存约 **18 MB**。之前版本的同类短时采样为 CPU 0.1%–0.2%、内存约 25 MB。显示精度、窗口是否打开和系统状态会影响这些数值；该结果不代表零功耗，也不能换算为电池续航提升比例。明确减少的是稳定状态的定时检查频率（约 75%），以及未锁定、故障暂停和非活动会话中的定时检查。

### 应用切换触发验证

修改触发方式后，24 项单元测试、Release 构建和 `bash Scripts/verify-integration.sh --include-system-pinyin --activate-apps` 均通过。

使用隔离的通知中心和可记录调用次数的输入源服务，验证：

- 未锁定期间等待 1.25 秒、锁定期间等待 1.3 秒，输入源及安全输入查询次数均为 0。
- 同一应用内更改输入源、只发送桌面变化通知、打开菜单，均不会自动恢复。打开菜单仅更新显示。
- 3 次快速应用激活合并为一次切换请求和一次累计计数，最后一次激活后约 200 毫秒执行。
- 每次激活至多进行一次切换，未确认成功时仅做一次结果确认；连续 3 次检查失败后暂停，无后台重试循环。
- 故障与安全输入暂停期间无周期性查询；安全输入结束后等待下次应用激活再恢复。
- 屏幕、休眠和会话通知会取消待执行任务；返回后等待应用激活。解锁或停止控制器也会取消排队的检查。

四种真实输入源分别执行 3 次恢复验证：先切到其他输入源，等待 300 毫秒确认不自动切回，再通过隔离通知中心发送应用激活事件。12 次从事件发出到观察到恢复的耗时为 **206.4–221.8 毫秒**，含约 200 毫秒的事件合并等待。每次成功只增加 1，累计值可持久化。

另外接入真实 `NSWorkspace` 通知，实际依次激活 Safari、文本编辑、终端和 Safari，确认切换后保持目标。真实安全输入的暂停/继续、启动时恢复、唤醒后等待应用切换、频繁争抢暂停及手动重试均通过。

## 仍需手动验收的系统交互

下面的物理会话操作与界面交互未由本轮自动化执行；通知注入和状态机验证不能替代它们。

| 操作 | 预期结果 |
| --- | --- |
| 点击菜单栏锁定、解锁、设置和退出 | 操作生效，菜单状态正确，设置窗口可正常打开 |
| 按系统输入源快捷键、点击系统输入法菜单 | 同一应用内保持切换结果；下次切换应用时恢复锁定目标 |
| 在普通文本框连续输入并切换应用 | 切换应用后恢复目标；观察并记录切换间隙中的实际字符行为 |
| 锁定后真正睡眠，再唤醒 | 等待下一次应用切换再检查目标 |
| 锁屏并重新解锁、快速切换用户会话 | 非活动会话不争抢，返回后的应用切换才触发恢复检查 |
| 退出并重新打开正式 `.app` | 恢复上次目标和锁定状态；故障暂停仍需手动重试 |
| 禁用锁定目标，再重新启用 | 下次检查显示目标不可用；重新启用后可手动恢复 |
| 将应用移入“应用程序”，开启登录启动，注销后重新登录 | 应用自动进入菜单栏并恢复状态 |
| 关闭登录启动后重新登录 | 不再自动启动 |

登录启动通过 `SMAppService.mainApp` 实现，包括错误与需要系统批准的状态显示。新应用标识的登录启动默认关闭，注销后自动启动仍需手动验收。
